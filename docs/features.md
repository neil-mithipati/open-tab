| feature | benefit |
|---|---|
| Typecheck gate fixed on main (OT-116) | Internal build hygiene, no user-facing change. Two stale errors in test files (`src/__tests__/setup.ts`, `ReceiptSplitStep.test.tsx`) were making the required `typecheck` gate fail on main, which meant no task in the backlog could be honestly marked done. Fixing both unblocked every other task's gate; 187 tests across 12 files still pass. |
| Account deletion (OT-111) | Delete your account and your data — photos, tabs you created, friendships, contacts — with one typed confirmation, no support ticket needed. Your entries on tabs other people created stay reconciled: they keep the name and Venmo handle you used, unlinked from your account, and any charges get re-pointed to that tab's owner instead of vanishing. |
| Privacy policy page (OT-110) | Plain-language `/privacy` page — what's collected, how it's used, what's never done, and how to delete it — linked from the landing page and profile. Every claim on the page was checked against the actual shipped code, not written from intent. |
| Share/Done reliability fix (OT-119) | Closing a receipt right after sharing it no longer yanks you back to it a moment later, and tapping Done while a share is still saving can no longer overwrite the charges you just recorded. |
| Parallel-dispatch cap fixed (OT-117) | Internal build hygiene, no user-facing change. The hook limiting how many build agents run at once had a counter that only ever went up, wedging all work with zero agents actually running; fixed by matching each agent's start to its stop instead of grouping by type. |
| Replay-proof receipt parsing (OT-115, OT-123) | Stops unbounded paid Gemini calls from replaying one uploaded receipt in a loop, fully closed — including a receipt whose photo was blank or unreadable, which used to replay forever off a single upload. Five concurrent scans of the same receipt now cost exactly one Gemini call. Ships as migration 0020, which must be applied before the code deploys or scanning goes down for every user. |
| Charge-row ownership check (OT-120) | Stops anyone from planting a charge row on someone else's tab by calling the API directly, instead of only through the app. Ships as migration 0019, which has not been applied to the live database yet — the fix is inert until it is. |
| Fleet build hygiene: dispatch cap hardened, agent config committed (OT-121, OT-125) | Internal build hygiene, no user-facing change. Closed three more ways the build-agent dispatch limit could silently let every agent through with no cap enforced, and brought the newest reviewer tier and a diagnostics tool under version control so they survive a clean checkout instead of existing in one working directory only. |
| Merge safety: genuine reverts no longer discarded (OT-126) | Internal build hygiene, no user-facing change. The tool that repairs a builder's worktree at merge time could mistake a deliberate revert to an earlier value for an accidental restore and silently drop it; it now refuses instead, while still catching the original accidental-restore case. |
| Parse-outage visibility (OT-132) | A parsing outage now tells you it's down and that you can enter items by hand, instead of showing a blank form that looked broken. |
| Claim-safe owner saves (OT-130, OT-133) | A person who joins your share link while you're still editing the receipt can no longer be silently deleted by your save. If they're not named in what you're about to save, the save is refused with a "someone just joined, reload" message instead of erasing them. If they are named, their claim and charge now survive the save too, instead of quietly disappearing while their name stays on the tab. |
| Claim status survives owner edits (OT-137) | A participant who marks their items done stays done after the owner edits and re-saves the receipt, instead of silently reading as still-claiming the moment anything else changes. |
| Retryable receipt scans (OT-134) | A dropped connection or brief scanning outage no longer costs you the receipt. Retry the same photo instead of re-uploading, capped at three attempts per receipt so the retry itself can't be used to force unlimited scans. |
| Receipt-image storage hardening: fourth unbound reader closed (OT-141) | Internal build hygiene, no user-facing change. Deleting a receipt now looks up its storage path through the one validated helper instead of a hand-copied parser, and skips the delete entirely rather than acting on an unvalidated path. The check that catches this class of bug was widened so the next copy-pasted parser fails a test instead of shipping. |
| Deployable storage-lockdown migration (OT-143) | Internal build hygiene, no user-facing change. The receipt-image storage migration could not be applied to a hosted database at all — Supabase's own storage tables are owned by a role no automated tool can assume. Split into a migration that pushes clean plus a versioned policy file and a documented dashboard procedure, so the storage lockdown from OT-139 can actually be turned on in production instead of only existing in a migration that fails on first run. The dashboard step still has to be done by hand — no automated path connects as the required role. |
| Schema-drift check (OT-145, OT-146) | Internal build hygiene, no user-facing change. `npm run check:drift` compares the repo against the live Supabase project — migrations against `schema_migrations`, and storage policies against `supabase/storage-policies.sql` by normalised expression rather than by name, since the dashboard renames policies on save. Fails loudly rather than reporting a false clean bill of health when credentials or the linked project are missing. On its first live run it found a real hole: the live `receipt_images_insert_own` policy was missing both its folder and ownership checks, letting any authenticated user write into another user's folder — still open, owner-side fix required. |
